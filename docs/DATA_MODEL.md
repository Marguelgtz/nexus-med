# Data Model — Medical Platform MVP

**Status:** Minimal prototype model proposal; confirm exact fields while implementing the documented workflows.  
**Database:** Local SQLite through Prisma ORM 7.  
**Owner:** Hono API only.

## 1. Design rules

- Model only the current patient and encounter workflows.
- Use relational constraints for patient/encounter relationships.
- Keep clinical note content attached to its encounter initially.
- Do not add document, user, clinic, appointment, billing, or authentication models in this prototype.
- Use stable internal identifiers; do not use names or contact details as keys.
- All demo fixtures are described in `DEMO_DATA.md`.

## 2. Current entities

### Patient

Represents one person receiving care.

Proposed fields:

| Field | Purpose | Notes |
|---|---|---|
| `id` | Stable internal identifier | UUID/string; generated by application or Prisma |
| `fullName` | Patient display name | Required |
| `dateOfBirth` | Date of birth | Optional date-only value (`YYYY-MM-DD`); for SQLite/Prisma, prefer a string representation to avoid timezone shifts |
| `phone` | Contact phone | Optional; no fake contact values in demo seed |
| `email` | Contact email | Optional; demo value should be absent or use reserved `.invalid` domain |
| `externalIdentifier` | Practice-specific identifier | Optional; confirm whether needed |
| `medicalConditions` | Relevant previous/current conditions | Optional free text in prototype |
| `previousSurgeries` | Previous surgeries | Optional free text |
| `allergies` | Allergies | Optional free text; blank means not recorded |
| `currentMedications` | Current medications | Optional free text |
| `isArchived` | Active/archive state | Default false; archival is reversible if implemented |
| `createdAt` | Creation timestamp | Required |
| `updatedAt` | Last update timestamp | Required |

Do not interpret empty medical-background fields as negative findings.

### Encounter

Represents one consultation or clinical interaction belonging to exactly one patient.

Proposed fields:

| Field | Purpose | Notes |
|---|---|---|
| `id` | Stable internal identifier | UUID/string |
| `patientId` | Owning patient | Required foreign key |
| `occurredAt` | When consultation happened | Required instant (`DateTime` in Prisma); may be corrected by doctor |
| `reason` | Reason for consultation | Optional free text |
| `historyOfPresentIllness` | Present illness history | Optional free text |
| `relevantHistory` | Relevant background considered for this encounter | Optional snapshot/free text; do not silently populate unsupported facts |
| `physicalExamination` | Doctor-entered findings | Optional free text |
| `assessment` | Doctor-entered assessment | Optional free text |
| `plan` | Doctor-entered plan | Optional free text |
| `followUp` | Follow-up instructions | Optional free text |
| `createdAt` | Record creation timestamp | Required; distinct from `occurredAt` |
| `updatedAt` | Last edit timestamp | Required |

The initial implementation does not require a separate `ClinicalNote` model, signatures, complex encounter states, or note versioning.

## 3. Relationships

```text
Patient 1 ───── N Encounter
```

- Every encounter belongs to exactly one patient.
- Deleting a patient must not silently cascade-delete clinical history. The prototype should use archive rather than permanent deletion.
- Server-side commands must verify the patient relationship when retrieving or updating an encounter.

## 4. Deferred entities

**Document:** Not implemented in this prototype. No document table, upload, storage key, or R2 integration should be created yet.

**User / Account / Session:** Not implemented. Google authentication remains pending.

**Clinic / Organization / Appointment / Billing:** Out of scope.

## 5. Indexes and constraints

At minimum, consider:

- Primary key on each entity.
- Foreign key `Encounter.patientId -> Patient.id`.
- Index on patient name for registry search where supported and useful.
- Index on `Encounter(patientId, occurredAt)` for patient timelines.
- Appropriate constraints for any practice-specific unique identifier once confirmed.

Do not add uniqueness to patient names, phone numbers, or email addresses.

## 6. Date and time handling

- Store date of birth as a date-only value (`YYYY-MM-DD` semantics), not as a timestamp that shifts with timezone.
- Store `occurredAt`, `createdAt`, and `updatedAt` consistently as instants.
- Display dates/times using the configured practice timezone, initially `America/Monterrey` unless the doctor specifies otherwise.
- Order the clinical timeline by `occurredAt`, newest first.
- The demo fixture supplies fixed ISO-8601 timestamps; seed logic must preserve them exactly.

## 7. Demo data

The initial local dataset must contain at least seven synthetic patients (six active) and at least nine synthetic encounters. It must include multiple encounters for some patients, one patient with no encounters, and one archived patient. See `DEMO_DATA.md` for seed behavior and presentation rules.

## 8. Open questions

- Exact required patient demographic fields.
- Whether a practice-specific identifier is needed.
- Whether structured medical-history tables are necessary later; use free text in the first prototype unless a real workflow requires structure.
- Whether the doctor needs vital signs as structured encounter fields in the first version.
- Whether encounters need drafts or amendments beyond explicit saved notes.
